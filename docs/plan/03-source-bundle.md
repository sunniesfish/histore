# 03. 상태 조회·소스 번들

상태: 상세화 중. 관련 결정: Q08, Q09, Q14. 근거: [번들 설계](../spec/project-history-design.md), [status/bundle 규약](../spec/core-cli-interface.md).

## 목표와 산출물

에이전트가 이유를 추측하지 않고 작성할 수 있도록 브랜치 또는 PR의 근거를 모은다. status, 소스별 수집, 트랜스크립트 추출, 번들 파일과 요약 응답을 구현할 계획이다.

## status 계약

--branch 또는 --pr 대상으로 repo, branch, drafts, skip, pr, entries, last_sync를 반환한다. PR 정보에는 번호·URL·상태·머지 시각·작성자·현재 사용자 여부가 포함된다. PR이 없으면 null이다. 인증·네트워크 실패를 PR 없음과 같은 것으로 처리할지는 정의되어 있지 않으므로 확정이 필요하다.

## 수집 대상

| 소스 | 기존 수집 방식 | 세부 결정 |
|---|---|---|
| 초안 | 브랜치별 drafts | PR 대상과 로컬 브랜치의 연결 |
| 트랜스크립트 | sessions.jsonl에서 세션 경로 조회, user/assistant 발화만 추출 | 세션 범위, 형식, 크기, 민감정보, 읽기 실패 |
| 이슈 | closing issues, Closes 패턴, 브랜치명 패턴 | 패턴과 우선순위, 중복, 타 저장소 이슈 |
| PR 본문 | gh pr view | 접근 불가와 빈 본문 구분 |
| 리뷰 | gh api | 페이지네이션, 댓글·리뷰 스레드 범위 |
| diff | git | 기준 브랜치, 미커밋·미추적 파일, 바이너리·rename |

## 수집 트리거 (Q17 확정)

세션 시작에는 현재 PR 존재·상태·기록 연결, 기존 기록의 갱신 대상 PR, 대기 질문 답글을 확인한다. 현재 PR에 기록이 없으면 안내만 하며 전체 번들은 기록 절차에서 수집한다. 특정 PR 기록 요청은 해당 PR의 상세 자료를 수집한다. 프로젝트 전체 과거·최근 PR 조회는 명시적 요청 또는 별도로 켠 검사에서 수행한다. 조회 범위·간격·한도는 추가 결정 대상이다.

## bundle 출력

- 대상은 branch 또는 #PR이다. --no-transcript와 --max-diff-lines 400이 기존 규약에 있다.
- Markdown 파일을 생성하고 path, sections, truncated를 JSON으로 반환한다.
- 섹션은 draft, transcript, issues, pr_body, reviews, diff_summary, diff 순서의 h2다.
- 도구 호출·출력과 트랜스크립트 원문은 번들에 넣지 않는다.
- Codex 트랜스크립트 파싱은 기존 설계상 best-effort이며 실패 시 해당 섹션을 생략한다. 실제 지원 형식은 확인이 필요하다.

## 추가 질문

- 여러 파일의 diff를 400줄로 제한할 때 배분과 잘림 표시 방식은 무엇인가?
- 대화·리뷰·이슈에는 각각 어떤 크기·기간 제한을 적용하는가?
- 수집원 일부가 실패하면 전체 실패와 부분 번들 중 어느 방식인가?
- 각 발화·인용의 출처와 시각을 어느 형식으로 보존하는가?
- 번들 재생성 시 덮어쓰기, 보존 기간, 파일 권한과 삭제 정책은 무엇인가?
- 사용자가 질문에 답한 내용과 단순 댓글을 수집 단계에서 구분하는가?

## 검증할 시나리오

로컬 브랜치·현재 PR·과거 PR·타인 PR 각각에 대해 수집원 연결을 확인한다. 빈 소스와 수집 실패를 구분하고, pagination·잘림·중복·트랜스크립트 생략을 검사한다. 도구 출력이 번들에 섞이지 않는 사례를 포함한다. 미결 항목의 기대값은 Q09 답변 후 확정한다.
