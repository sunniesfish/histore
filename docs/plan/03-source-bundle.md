# 03. 상태 조회·소스 번들

상태: 상세화 중. 관련 결정: Q08, Q09, Q14. 근거: [번들 설계](../spec/project-history-design.md), [status/bundle 규약](../spec/core-cli-interface.md).

## 목표와 산출물

에이전트가 이유를 추측하지 않고 작성할 수 있도록 브랜치 또는 PR의 근거를 모은다. status, 소스별 수집, 트랜스크립트 추출, 번들 파일과 요약 응답을 구현할 계획이다.

## status 계약

--branch 또는 --pr 대상으로 repo, branch, drafts, skip, pr, entries, last_sync를 반환한다. PR 정보에는 번호·URL·상태·머지 시각·작성자·현재 사용자 여부가 포함된다. PR이 없으면 null이다. 인증·네트워크 실패를 PR 없음과 같은 것으로 처리할지는 정의되어 있지 않으므로 확정이 필요하다.

## 수집 대상

| 소스 | 기존 수집 방식 | 세부 결정 |
|---|---|---|
| 초안 | 브랜치별 drafts | PR 대상과 로컬 브랜치의 연결 |
| 트랜스크립트 | Q09a: 같은 로컬 저장소·브랜치에 연결된 여러 세션의 user/assistant 발화를 기본 수집. Q09f: 최근 30일·최대 10만 자, 초과 시 잘림 표시. Q09b: 알려진 비밀값 형식을 로컬 번들 작성 전에 가리고 경고. 도구 호출·출력 제외, `--no-transcript` 허용 | 탐지 형식 목록, 읽기 실패·발화 경계 세부 |
| 이슈 | closing issues, Closes 패턴, 브랜치명 패턴 | 패턴과 우선순위, 중복, 타 저장소 이슈 |
| PR 본문 | gh pr view | 접근 불가와 빈 본문 구분 |
| 리뷰 | gh api | 페이지네이션, 댓글·리뷰 스레드 범위 |
| diff | Q09d: 기준 브랜치와 갈라진 뒤의 커밋 및 현재 작업 트리. staged·unstaged·ignore되지 않은 미추적 파일 포함 | 바이너리·rename 표시, 기준 브랜치 갱신 |

## 수집 트리거 (Q17 확정)

세션 시작에는 현재 PR 존재·상태·기록 연결, 기존 기록의 갱신 대상 PR, 대기 질문 답글을 확인한다. 현재 PR에 기록이 없으면 안내만 하며 전체 번들은 기록 절차에서 수집한다. 특정 PR 기록 요청은 해당 PR의 상세 자료를 수집한다. 프로젝트 전체 과거·최근 PR 조회는 명시적 요청 또는 별도로 켠 검사에서 수행한다. 조회 범위·간격·한도는 추가 결정 대상이다.

Q09a에 따라 대화 발화는 기록 절차에서 번들을 만들 때만 로컬로 추출한다. 세션 인덱스의 로컬 저장소 키와 브랜치 키가 모두 대상과 일치하는 세션을 포함한다. 대화 전체와 로컬 트랜스크립트 경로는 원격 엔트리에 기록하지 않는다. 수집 대상 기간·길이는 Q09f를 따른다.

Q09f에 따라 번들 생성 시점 기준 최근 30일의 발화를 최대 10만 자까지 수집하며 최신 발화를 우선한다. 기간·크기 제한으로 제외한 발화가 있으면 번들 본문과 결과의 `truncated`에 `transcript`를 표시한다. 정상적인 제한은 Q09c의 수집 실패와 구분한다. 발화 경계에서의 절단·문자 수 계산 방법은 구현 계약에서 정한다.

Q09b에 따라 추출한 발화에서 알려진 비밀값 형식을 메모리에서 탐지해 일치한 값 전체를 `[REDACTED]`로 대체한 뒤 번들을 쓴다. 결과에는 가림 여부·건수를 경고로 담고, 원문이나 일부 문자는 경고·진단 로그에 쓰지 않는다. 탐지할 구체 형식 목록과 누락·오탐 fixture는 구현 전 정한다. 자동 가림은 모든 민감정보를 찾아내지 못할 수 있다.

Q09c에 따라 일부 수집원이 실패해도 확보한 자료로 번들을 만든다. 결과에는 `partial: true`와 실패한 수집원의 이름·사유 코드를 `unavailable`에 담는다. 원래 자료가 없는 경우는 실패로 세지 않는다. 모든 시도가 실패해 사용 가능한 자료가 없다면 exit 1이다. 부분 번들만으로 원격 기록을 허용하지 않으며 Q07a의 결정 내용·출처 최소 요건을 별도 검증한다.

Q09d에 따라 로컬 브랜치는 PR이 있으면 PR 대상 브랜치, 없으면 원격 기본 브랜치와의 merge-base부터 현재 작업 트리까지를 수집한다. 커밋된 변경뿐 아니라 staged·unstaged 수정·삭제와 ignore되지 않은 미추적 파일도 포함한다. 외부 PR처럼 연결된 로컬 작업 트리가 없으면 PR의 base/head diff만 수집한다. 기준 브랜치를 판정할 수 없으면 diff 수집 실패로 표시하고 Q09c의 부분 번들 규칙을 따른다. skip의 실질 변경 스냅샷도 같은 범위를 사용하되 자동 판정에는 `watch` 범위를 적용한다(Q06e). 명시적 번들은 전체 변경을 수집한다. stage 이동·커밋만으로 최종 파일 내용이 같다면 skip을 무효화하지 않는다(Q08f). 세부 스냅샷 정규화는 후속 결정이다.

Q09e에 따라 기록 절차에서 생성한 로컬 번들은 해당 기록의 원격 저장 성공이 확인되면 삭제한다. 저장이 실패·중단되거나 로컬 초안 작성까지만 끝나면 재시도를 위해 보존한다. 연결되지 않은 다른 번들과 원본 트랜스크립트는 이 삭제 대상이 아니다.

## bundle 출력

- 대상은 branch 또는 #PR이다. --no-transcript와 --max-diff-lines 400이 기존 규약에 있다.
- Markdown 파일을 생성하고 path, sections, truncated를 JSON으로 반환한다.
- 섹션은 draft, transcript, issues, pr_body, reviews, diff_summary, diff 순서의 h2다.
- 도구 호출·출력과 트랜스크립트 원문 전체는 번들에 넣지 않는다. 추출한 사용자·에이전트 발화에는 Q09b의 비밀값 가림을 적용한다.
- Codex 트랜스크립트 파싱은 기존 설계상 best-effort이며 실패 시 해당 섹션을 생략한다. 실제 지원 형식은 확인이 필요하다.

## 추가 질문

- 여러 파일의 diff를 400줄로 제한할 때 배분과 잘림 표시 방식은 무엇인가?
- 리뷰·이슈에는 각각 어떤 크기·기간 제한을 적용하는가?
- 부분 번들에서 실패 사유 코드와 소스별 타임아웃을 어떻게 정의하는가?
- 각 발화·인용의 출처와 시각을 어느 형식으로 보존하는가?
- 번들 재생성 시 덮어쓰기, 실패·독립 생성 번들의 장기 보존 기간, 파일 권한과 정리 방식은 무엇인가?
- 사용자가 질문에 답한 내용과 단순 댓글을 수집 단계에서 구분하는가?

## 검증할 시나리오

로컬 브랜치·현재 PR·과거 PR·타인 PR 각각에 대해 수집원 연결을 확인한다. 빈 소스와 수집 실패를 구분하고, pagination·잘림·중복·트랜스크립트 생략을 검사한다. 도구 출력이 번들에 섞이지 않는 사례를 포함한다. 미결 항목의 기대값은 Q09 답변 후 확정한다.

Q09c fixture는 트랜스크립트 실패·PR 본문 성공의 부분 번들, 정상적인 빈 소스, 전부 실패한 경우의 exit 1, 부분 번들에서 최소 기록 요건 불충족을 구분한다.

Q09d fixture는 PR 전·후 기준, 커밋 전후 동일 파일 내용, staged·unstaged 수정·삭제, ignore되지 않은 미추적 파일, 외부 PR, 기준 브랜치 판정 실패를 포함한다.

Q09b fixture는 탐지한 비밀값이 번들·JSON 경고·stderr 어디에도 원문 또는 일부 문자로 남지 않는지, 여러 건의 경고 건수가 맞는지 확인한다. 알려지지 않은 형식은 탐지 보장을 하지 않음을 안내에 명시한다.

Q09e fixture는 원격 저장 성공 시 연결된 번들만 삭제하고, 전송 실패·중단 또는 로컬 초안 작성만 완료된 경우에는 보존하는지 확인한다.

Q09f fixture는 기간 안팎의 세션, 10만 자 초과, 제한으로 제외된 발화가 없는 경우를 구분하고, 잘림 표시가 수집 실패인 `partial`·`unavailable`을 켜지 않는지 확인한다.
